# 作業を「案内ルート」として登録・実行する

このExecPlanは作業中に更新する。`hub/AGENTS.md` と `docs/ARCHITECTURE_LAYERING_POLICY.md` に従う。

## 目的

現在の平坦な栽培作業を廃止し、判断、観察、測定、準備、実施、待機、完了確認を順序と分岐で結ぶ「案内ルート」を作業の正規モデルにする。利用者はプログラマ向けのノード図を編集せず、現場の言葉でステップと回答後の進み先を登録できる。実行時は現在の一手だけを中心に表示し、完了済み、現在地、次の候補、開始を妨げる依存関係を迷わず確認できる。

## 進捗

- [x] 既存 `work_plan`、固定三段判断UI、作業記録、見送り、依存関係の不足を調査した。
- [ ] 案内ルート定義・実行状態・入力検証・旧作業削除方針を実装する。

- [ ] 現場向け登録UIと「現在の一手」中心の実行UIを実装する。
- [ ] バックエンド、型、ビルド、ブラウザ回帰と目視確認を完了する。

## 設計判断

- 内部は有向グラフ、通常UIは縦方向の案内ルートと現在ステップカードにする。自由配置キャンバスや条件式入力は提供しない。
- ステップ種別は `observe`、`measure`、`decide`、`prepare`、`perform`、`wait`、`verify` とする。
- 分岐は各ステップの回答候補に `next_step_id` を持たせる。一本道はステップ自身の `next_step_id` を使う。
- センサー欠測はエラー終了ではなく、測定ステップの `missing_step_id` から手動確認へ進める。
- ルート定義と実行状態を分離し、実行時の回答、使用値、担当者、時刻を監査可能に保存する。
- 作業間依存はルート単位の `dependencies` とし、完了・承認・経過日数を最初の対象にする。
- 既存のカレンダー作業は互換移行しない。保存データの正規化時に旧 `actions` と関連する未確定作業状態を空にし、新しい案内ルートだけを表示する。
- AIは案内ルート案を生成できるが、分岐評価、依存解除、センサー鮮度、安全条件はHubの決定的ロジックで扱う。

## 実装方針

1. `PlantManagementRepository` に案内ルートの正規化、循環・参照検証、CRUD、実行開始、ステップ回答を追加する。旧作業を読み込み時に破棄し、保存形式へ `work_routes` と `work_route_runs` を追加する。
2. Flask APIは入力変換とHTTP応答に限定し、一覧、作成、更新、削除、開始、ステップ回答を公開する。
3. TypeScript型とAPIクライアントを追加し、栽培カレンダーの作業領域を案内ルート一覧へ置き換える。
4. 登録UIは基本情報、順序付きステップ、回答候補と進み先、欠測時の進み先、依存関係をフォームで編集する。
5. 実行UIは進捗、現在の一手、選択肢、完了済みの道のり、次の候補を表示する。

## 受入条件

- 旧作業カードが表示されず、新規案内ルートを登録できる。
- 判断回答に応じて次のステップが変わる。
- 測定値がない場合に手動確認ステップへ進める。
- 依存ルートが未完了の場合は開始できず、理由が表示される。
- ページ再読込後も現在ステップと回答履歴が復元される。
- 完了時に案内ルート実行履歴が残り、同じルートを再実行できる。
- デスクトップとモバイルで横方向のグラフ操作を要求しない。

## 回復性

旧作業を削除する破壊的移行であるため、適用前の状態ファイル・DBバックアップを必須とする。新フィールドは独立しており、実装をrevertしてバックアップを戻せば旧表示へ復旧できる。案内ルートAPIは同じ操作を再送しても壊れないよう、ステップ回答済み状態を検証する。
