## 1. 目的

作物を定植した後に「いつ、何を、なぜ行うか」を利用者が判断できるようにする。設置ビュー上の場所と作物を結び付け、定植条件に応じた管理カレンダー、時期サジェスト、作業記録、質問回答を一つの運用フローとして提供する。

対象作業には追肥、防除、剪定、環状剥皮、受粉、ジベレリン処理、収穫、植え替え、潅水、観察、越冬管理などを含める。ただし、すべての作業を必須とは扱わない。

## 2. 責務分離

| 要素 | 責務 |
|---|---|
| 設置レイアウト | 圃場、空間、鉢、畝などの場所と形状を管理する |
| 定植情報 | どの配置に何をいつ定植したか、品種、株数、栽培方式、条件、目標レンジを管理する |
| 管理カレンダー | 定植単位ごとの作業候補、期間、優先度、理由、タグ、状態を管理する |
| LLM | 新規定植時の栽培基準・目標レンジ・初期カレンダー生成、反復作業完了後の次回タスク生成、質問回答を行う |
| 作業記録 | 利用者が実際に行った日付、メモ、5段階評価、画像を確定情報として保存する |
| R2 | 作業・観察画像のオブジェクト本体を非公開で保存する |
| Device Hub | 期日判定、サジェスト、永続化、編集差分の再利用を統括する |

LLM の出力は提案であり、定植情報や作業実績そのものではない。利用者が選択した実施日を作業実績の正とする。

### 2.1 実装モジュールの境界

| 層 | 実装 | 置くもの |
|---|---|---|
| ドメインカタログ | `plant_action_catalog.py` | 作業種別、表示名、検索語、イラスト、色。画面ごとに同じ定義を複製しない |
| 作業計画カタログ | `plant_work_catalog.py` | 追肥、剪定、潅水、防除など全作業の既定対象、確認点、方法候補 |
| 永続化・生成 | `plant_management_repository.py` | 定植、カレンダー、作業実績、LLM生成結果の保存と更新 |
| 表示モデル | `field_calendar_view.py`、`field_record_calendar.py`、`field_status_dashboard.py` | TODO、記録カレンダー、状態指標をテンプレート用データへ変換する純粋処理 |
| HTTP | `web_server.py` | requestの検証、repository呼び出し、response生成。表示データの計算規則を持たない |
| 管理UI | `admin-ui/src/plant-calendar/` | ドロワー、年間ガント、作業カード。API通信やページ全体の状態は `App.tsx` が統括する |

新しい指標や作業表示を追加するときは、ドメイン定義をカタログへ、表示上の組み立てを表示モデルへ置く。Flask route、Jinja template、React pageへ同じ変換規則を重複実装しない。表示モデルはFlaskに依存させず、入力辞書から出力辞書を作る単体試験可能な関数とする。

## 3. 基本フロー

1. 設置ビューで鉢、畝、植木、水耕ベッドなどを配置して保存する。
2. 配置を選択し、作物名、品種、作物区分、果樹の場合の樹齢、定植日、株数、栽培方法、用土、日当たり、補足、AI計画への要望を登録する。用土・培地と日当たりはドロップダウンから選択し、地域は圃場の所在地を使用して培地へ重複入力しない。
3. Hub は登録条件と同一作物の採用済み修正例を LLM へ渡し、潅水・施肥・EC・pHの管理方針、反復規則、目標レンジ、12か月分の初期カレンダー案を一度の呼び出しで生成する。
4. 利用者は生成した目標レンジをスライダーで編集できる。
5. LLM が未設定または応答不正の場合は、決定的な標準カレンダーを生成する。
6. Hub は現在日と作業期間を比較し、`期限超過`、`今やる`、`まもなく`をサジェストする。
7. 利用者は作業の理由と優先度を確認し、実行、編集、見送りを判断する。
8. 作業後に実施日、対象、実施方法、使用資材、次回確認までの日数、任意メモ、絵文字による5段階評価、任意画像を入力し、全作業で同じ実績構造として保存する。
9. 完了した作業に `completion_date` 起点の反復規則がある場合、Hub は保存済み栽培基準、実施日、既存予定だけを LLM へ渡し、次回タスクを最大3件生成する。
10. 利用者が明示的に許可した編集差分は、同じ作物の次回カレンダー生成時の参考例にする。

AI計画生成は、作物名、作物区分、定植日、株数、栽培方式、用土・培地、日当たり、および果樹の場合の樹齢が揃うまで開始しない。ボタン無効時は不足項目を画面上に列挙する。APIも定植レコード作成とLLM呼び出しの前に同じ条件を検証し、不完全な要求によるAPI消費を防ぐ。

定植登録直後は、生成結果を設置ビューの上に全画面モーダルで表示する。通常の閲覧は `/fields/<field_id>/calendar?planting=<planting_id>` の年間カレンダー専用ページを使用し、設置Canvasを同時に開かない。ガントは既定で今月から12か月を表示し、開始月と6・12・24か月の表示幅を変更して過去の予定・実施記録も閲覧できる。

## 4. データモデル

### 4.1 定植情報

| 項目 | 内容 |
|---|---|
| `field_id` | 圃場 ID |
| `space_id` | 設置レイアウト内の空間 ID |
| `placement_id` | 鉢、畝などの配置 ID |
| `placement_name` | 登録時の配置名 |
| `crop_name` / `cultivar` | 作物名、品種 |
| `crop_category` | `vegetable`、`fruit_tree`、`flower`、`herb`、`other` |
| `tree_age_years` | 果樹の樹齢。果樹以外は `null` |
| `planted_on` / `plant_count` | 定植日、株数 |
| `cultivation_method` | 鉢植え、露地、養液など |
| `conditions` | 環境、用土・培地、日当たり、補足。地域は互換項目として空値を保持し、生成時は圃場所在地を使う |
| `growth_targets` | 土壌水分、土壌 EC、土壌 pH、湿度、PAR の下限・上限。未設定指標は `null` |
| `status` | `active`、`harvested`、`removed` |
| `calendar_id` | 対応する管理カレンダー ID |

同じ `field_id` と `placement_id` に複数の active 定植を登録してはならない。配置を移動しても ID を維持する限り定植情報との関連は維持される。

目標レンジは圃場ではなく定植に属する。複数作物が同じ圃場にある場合でも、鉢・畝ごとに異なる目標を保持できる。センサーまたは潅水デバイスの `target_placement_ids` と `placement_id` を照合し、現在値の判定に使う目標を決定する。

### 4.2 カレンダー作業

| 項目 | 内容 |
|---|---|
| `action_type` | 作業種別カタログの正規コード。表示名、検索語、イラストを作業データに重複保存しない |
| `title` | 利用者が判断できる作業名 |
| `priority` | `required`、`should`、`recommended`、`optional` |
| `window_start` / `window_end` | 実施候補期間 |
| `timing_label` | 活着後、休眠期などの生育上の目安 |
| `reason` | なぜ行うか |
| `instructions` | 何を確認し、どう作業するか |
| `tags` | 結実、樹勢維持、病害虫予防、追肥などの目的 |
| `required_people` | 同時に必要な人数。1〜100人の整数 |
| `estimated_minutes` | 1回の作業に必要な見積時間。安全確認と記録を含む1〜1440分の整数 |
| `work_plan` | 全作業が持つ、作業対象、開始・見送り条件、確認点、方法候補、完了条件 |
| `status` | `planned`、`in_progress`、`completed`、`skipped` |
| `completion` | 実施日、作業記録 ID、メモ |
| `source` | LLM、標準提案、利用者編集の区別 |
| `rule_id` | 作業インスタンスを生成した反復規則 ID |

作業種別は `plant_action_catalog.py` を source of truth とする。現行コードは `fertilization`、`pest_control`、`pruning`、`girdling`、`pollination`、`gibberellin_treatment`、`harvest`、`repotting`、`watering`、`observation`、`winter_care`、`other` とする。API は定植バンドルの `action_types` で正規コード、表示名、TODO名、イラストURL、強調色、検索語を返す。既存データの「追肥」「灌水」「ジベ処理」などは読み込み時に正規コードへ正規化する。

初期イラストは視覚識別効果の高い追肥、防除、剪定、受粉、ジベレリン処理、収穫、潅水の7種に用意する。未生成の種別は共通アイコンにフォールバックし、画像の有無で作業登録可否を分けない。画像は作業の種類を識別するための補助であり、実施量、希釈倍率、安全上の指示は `instructions` と製品ラベルを正とする。

全作業の `work_plan` は次を持つ。防除だけの個別モデルは作らず、追肥、剪定、潅水、受粉、収穫なども同じ構造で扱う。

| 項目 | 内容 |
|---|---|
| `targets` | 根域、対象枝、花房、果実、病害虫など、今回作業または確認する具体的な対象 |
| `start_conditions` | 作業を開始してよいと判断する観察値、時期、状態 |
| `skip_conditions` | 延期、中止、追加確認に切り替える条件 |
| `checkpoints` | 葉色、EC、花芽、剪定適期、土壌水分、病斑など、実施判断と作業後に見る点 |
| `method_options` | 手作業、設備、肥料・資材、農薬、観察のみなど、選択可能な実施方法 |
| `completion_criteria` | 作業を完了と判断し、実績へ残す確認事項 |

`method_options` は利用者が実施時に選択できる代替案であり、次の固定形式を持つ。

| 項目 | 内容 |
|---|---|
| `id` / `label` / `method_type` | 安定ID、表示名、観察・手作業・設備・資材・農薬などの区分 |
| `purpose` | この方法を選ぶ目的 |
| `application_method` | 対象へどのように実施するか |
| `amount_or_rate` | 使用量、希釈倍率、処理時間。根拠がない場合は推測値ではなく確認行動を記載 |
| `procedure_steps` | 準備から終了まで実行順に並べた手順 |
| `completion_checks` | この方法の終了時に確認する事項 |
| `precautions` | 安全、見送り、ラベル制限、作物を傷めないための注意 |
| `frequency` | 実施方式、最小・標準・最大間隔、最大回数、判断根拠 |
| `material_name` / `registration_number` | 根拠を確認できた資材・製品名と登録番号 |
| `follow_up_days_default` | 作業後に状態を再確認する目安日数 |
| `source_name` / `source_url` / `source_checked_at` | 候補を検証した情報源 |

`method_type` は `observation`、`manual`、`device`、`material_application`、`chemical`、`physical`、`biological`、`cultural`、`other` とする。`frequency.mode` は `one_time`、`as_needed`、`interval`、`seasonal`、`continuous` とする。

| 作業種別 | `targets` の例 | `checkpoints` の例 | `method_options` の例 |
|---|---|---|---|
| 追肥 | 根域・培地、葉と新梢 | 葉色、樹勢、土壌・排液EC、前回施肥量 | 固形肥料、液肥、今回は見送る |
| 剪定 | 枯枝、交差枝、徒長枝、混み合った枝葉 | 剪定適期、花芽・結果枝、樹形、採光 | 剪定、芽かき・摘心 |
| 潅水 | 根域・培地 | 潅水前後の土壌水分、排水、天候 | 手動潅水、潅水設備 |
| 防除 | 病害虫、葉、新芽、株元 | 虫体、卵、食害、病斑 | 観察、物理的防除、登録根拠付き薬剤候補 |

肥料、農薬、ジベレリン等の資材名は、外部情報または利用者入力で確認できた場合だけ `material_name` に入れる。特に農薬候補は登録番号と情報源を保持し、外部登録情報から検証していない商品名をLLMの記憶だけで追加してはならない。旧 `pest_control`、`observation_points`、`product_name`、`effective_days_default` は読み込み時だけ新形式へ移行し、新規保存には使用しない。

画像は `static/plant-actions/` へ WebP で格納する。ComfyUI の Krea2 ワークフローで再生成する場合は、ジョブ定義 `data/plant_action_image_jobs.json` と `scripts/generate_plant_action_assets.py` を使う。既定の `http://127.0.0.1:8188` に接続できない WSL 環境では、script が `http://host.docker.internal:8188` も試行する。

### 4.3 栽培基準と反復規則

初回生成結果は作業日付だけでなく、後続判断に再利用する `care_profile` と `task_rules` をカレンダーへ保存する。

`care_profile` は潅水方針と基準間隔、潅水の開始・見送り条件、施肥方針、EC・pH管理、ステージ別管理、前提、根拠情報を持つ。`task_rules` は `rule_id`、作業種別、反復方式、起点、最小・標準・最大間隔、対象月、実施条件、見送り条件を持つ。

反復方式は次を正とする。

| 値 | 用途 |
|---|---|
| `one_time` | 定植、初回整枝など一回限り |
| `interval_after_completion` | 追肥など、実際の前回実施日から間隔を数える |
| `seasonal` | 剪定、越冬管理など季節窓を優先する |
| `condition_based` | 土壌水分、EC、病徴など現在条件で判断する |
| `continuous_review` | 定期観察や病害虫確認 |

起点は `planting_date`、`completion_date`、`calendar_date`、`observation` から選ぶ。追肥のように作業遅延が次回へ影響するものは `completion_date` とし、元の予定日を次回計算に使わない。

## 5. 優先度と時期

優先度と時期は別の概念として管理する。

| 優先度 | UI 表示 | 意味 |
|---|---|---|
| `required` | 必須 | 作物維持や安全上、原則として実施または確認が必要 |
| `should` | やった方がよい | 条件に合えば実施価値が高い |
| `recommended` | おすすめ | 品質、収量、観察精度の改善候補 |
| `optional` | 好みで | 仕立て方や狙いによって選択する作業 |

| 時期状態 | 判定 |
|---|---|
| `overdue` | 現在日が `window_end` より後 |
| `due` | 現在日が開始日から終了日の範囲内 |
| `upcoming` | 開始日の 14 日前から前日まで |

実施済みと見送り済みの作業はサジェスト件数に含めない。

候補期間は作業カードの補助テキストではなく主情報として、カード先頭に `作業期間`、開始日、終了日、生育上の時期を高コントラストで表示する。状態色は `期限超過`、`今やる`、`まもなく`、実施済みを区別し、未選択を意味する灰色だけで期間を表現しない。年間ガントも優先度ごとの色を保ち、現在日を縦線で示す。

## 6. LLM 利用方針

### 6.1 初回栽培基準・カレンダー生成

入力には圃場所在地、空間、配置、定植条件、作物区分、樹齢、生成基準日、12か月の期間、利用者の要望、同じ作物の採用済み修正例を含める。出力は `care_profile`、`growth_targets`、`task_rules`、最大24件の `actions` を持つ JSON オブジェクトに限定する。目標値の物理範囲、日付、優先度、作業種別、反復方式をサーバで検証してから保存する。不正な目標指標だけを標準値で補完し、旧形式の応答に栽培基準がない場合は標準基準と規則を補完する。

初回プロンプトは次を要求する。

- 固定間隔だけで潅水を断定せず、培地、鉢容量、季節、降雨、土壌水分、排液EC、排水状態の開始・見送り条件を返す。
- 追肥は前回実施日を起点にできる最小・標準・最大間隔、対象月、葉色、樹勢、EC、結実負担、生育休止による判断条件を返す。
- ECは `uS/cm`、PARは `umol/m2/s` とし、適用できない目標は `null` にする。
- 不明事項を断定せず `assumptions` に残す。入力に根拠資料がない場合は `knowledge_sources` を空配列にし、架空の出典を作らない。
- 初期予定の各作業を `rule_id` で反復規則へ結び付ける。
- 全作業に `work_plan` を付け、作物、時期、生育段階に即した対象、開始条件、見送り条件、確認点、方法候補、完了条件を返す。「確認する」「作業する」「適宜」「適量」だけの抽象的な候補にしない。
- 追肥は肥料・施肥方法と葉色・樹勢・EC、剪定は対象枝と残す枝・花芽、潅水は対象培地と水分・排水、受粉は花・花房と開花状態を具体化する。
- 防除作業は作物名と時期に即した具体的な確認対象名と観察箇所を返す。薬剤候補は入力済みの `validated_pesticide_candidates` だけを転記し、製品名、登録番号、適用方法、使用量・希釈、使用間隔・回数、収穫前日数を固定フィールドへ対応させる。候補がない場合は `chemical` を作らず、非化学的手段と登録情報の確認手順を返す。
- 肥料、農薬、植物成長調整剤の製品名や数値は、根拠URL付きの検証済み候補にある値だけを使う。候補にない値をLLMの記憶で補わない。

### 6.1.1 利用者の習熟度

個人設定 `cultivation_experience` は `beginner`、`standard`、`professional` の3段階とし、認証email単位でTursoへ保存する。初回計画、指定日からの再生成、作業完了後の差分タスク生成は同じ設定を参照する。

| 設定 | プロンプト方針 |
|---|---|
| `beginner` | 専門用語へ短い説明を付け、準備・実施・終了確認を3〜7段階で示す。開始、見送り、完了をどこで判断するか平易に書く |
| `standard` | 作業前判断、2〜6段階の手順、終了確認、次回判断を簡潔に示す。必要な用語と単位は維持する |
| `professional` | 初歩説明を省き、適用条件、判断閾値、処理量、頻度、制約、根拠を優先する。根拠にない数値は補完しない |

習熟度が変えるのは説明量、用語補足、情報の優先順位である。安全条件、製品ラベル確認、単位、開始・見送り条件、完了確認はどの設定でも省略しない。未設定または未知の値は `standard` として扱う。

LLM 呼び出しに失敗した場合、API キーがない場合、JSON が不正な場合は標準提案へフォールバックする。したがって、定植登録は外部 AI の可用性に依存しない。

初回生成は外部APIコストが発生するため、登録ボタンは `定植を登録してAI計画を生成` と明示する。生成前には利用者が補足条件を編集できる。生成後は次の操作を提供する。

- 現在日または指定日を基準に、追加要望を編集して12か月計画を再生成する。
- 再生成時は完了済み作業を維持し、未実施の生成作業だけを置き換える。
- 作業を手動追加、編集、削除する。完了済み作業は履歴保全のため削除しない。
- 現在月から12か月をガントチャートで俯瞰し、下段の作業詳細へ移動する。

### 6.2 完了実績からの次回タスク生成

反復作業を完了したときは、初回プロンプトを再実行しない。保存済み `care_profile`、該当する `task_rule`、完了作業、利用者が選択した実施日、直近作業履歴、既存の未完了予定を差分タスクプロンプトへ渡す。

差分タスクプロンプトは次を制約する。

- 新しい栽培知識や目標レンジを生成し直さない。
- 元の予定日ではなく `performed_on` を次回間隔の起点にする。
- `work_details.execution` の対象、実施方法、使用資材、`follow_up_days` を全作業で判断材料にする。
- 追肥後は葉色・樹勢・EC、剪定後は切り口と新梢、潅水後は水分と排水、防除後は再発・残存など、作業種別に応じた次回確認点を返す。
- `active_months` 外に出る場合は次の適期へ移動する。
- 既存の未完了予定と重複させない。
- 次回が不要なら空配列を返す。
- 一回の出力は次回に必要な0〜3件だけとする。

LLMが無効または失敗した場合も、Hubは保存済みの標準間隔と対象月から次回期間を決定的に算出する。作業記録の保存はLLM呼び出しの成否に依存させない。

### 6.3 呼び出しタイミングとコスト制御

| イベント | LLM | 理由 |
|---|:---:|---|
| 新規定植 | 1回 | 栽培基準、目標、反復規則、初期12か月計画を作る |
| 作物・栽培方式・所在地など基準条件の変更 | 利用者確認後に1回 | 保存済み基準の再構築が必要 |
| 利用者による12か月計画の再生成 | 1回 | 明示的なコスト発生操作 |
| `completion_date` 起点の作業完了 | 1回 | 実施日と季節から該当作業の次回だけを作る |
| 日次TODO表示・期限更新 | なし | 保存済み期間をHubで比較する |
| センサー値受信 | なし | 閾値・ルールエンジンで即時判断する |
| ページ表示・Hub再起動 | なし | 保存済み結果を読む |
| 作物名・病害虫名・薬剤名の入力候補表示 | なし | ローカル検索インデックスを使う |
| 農薬登録データの同期 | なし | 外部API/CSVの差分取得と正規化だけを行う |

日次処理では `overdue`、`due`、`upcoming` の状態だけを再計算する。全作物を毎日LLMへ送らない。将来、気象予報や積算温度による大幅な日程補正を追加する場合も、一日一回のバッチで変更候補を作り、同一入力ハッシュでは再呼び出ししない。

### 6.4 栽培根拠の取得とキャッシュ

現行実装はモデル知識から薬剤名を生成せず、外部サイトを自動検索しない。生産運用ではLLMの前段に `CropKnowledgeProvider` と `PesticideKnowledgeProvider` を置き、都道府県の栽培指針、農業試験場・普及機関、品種提供元、農薬登録情報など、出典と適用地域を保持できる情報だけを取得する。

検索キーは正規化した作物、品種、作物区分、樹齢帯、栽培方式、培地、屋内外、都道府県とする。取得結果をバージョン付き栽培基準としてキャッシュし、同じ条件の再生成や完了後タスク生成では再取得しない。資料更新、利用者による基準再生成、基準条件変更時だけキャッシュを更新する。取得本文をそのまま命令として扱わず、出典URL、発行者、発行日、適用地域、取得日時を構造化してプロンプトへ渡す。

#### 6.4.1 農薬情報源の調査結果

FAMICは実使用時に個々の製品ラベルを確認するよう明記している。したがって、本システムは登録候補を絞り込んでも「使用可」を最終確定せず、作物名、対象病害虫、使用時期、希釈・使用量、使用方法、本剤と有効成分の総使用回数、収穫前日数を利用者が現物ラベルと照合できる表示にする。

#### 6.4.2 低コスト検索パイプライン

1. 外部providerから取得したスナップショットを登録番号を主キーに正規化する。
2. 作物名、病害虫名、製品名、有効成分の表記揺れ辞書と全文検索インデックスをHub側に構築する。
3. 入力中のサジェストはローカルインデックスだけで返し、LLMを呼ばない。
4. 作物、対象病害虫、基準日、使用時期、登録失効、使用方法で候補を決定的に絞り込む。
5. 初回カレンダー生成時だけ、絞り込んだ登録番号付き候補を `validated_pesticide_candidates` としてLLMへ渡し、時期と理由の説明を生成する。
6. 作業完了時は利用者が選んだ候補または自由記述を実績へ保存し、反復規則がある場合だけ差分LLMを最大1回呼ぶ。LLMが無効なら全作業共通の `follow_up_days` と規則で再確認日を算出する。
7. 同じスナップショット版、作物、病害虫、地域、栽培条件の結果をキャッシュし、ページ表示や文字入力では再生成しない。

外部データ同期とLLM生成を同じ処理にしない。provider障害時も保存済みスナップショットを検索でき、LLM障害時も作業記録と決定的な次回確認を継続できる構成とする。

#### 6.4.3 Agent skillの位置付け

`agro.jp`を検索するCodex skillは、開発者が手動調査する補助にはできるが、Device Hubの実行時機能にはしない。skillは画面スクレイピングの利用条件、DOM変更、実行環境に依存し、複数利用者の同時操作、キャッシュ、監査、登録情報の版管理を担えないためである。

実行時は `PesticideKnowledgeProvider` adapterとローカル検索APIを正とする。将来Agent向けskillを追加する場合も、この検索APIを呼び、登録番号、データ版、取得日時、根拠URLを返す薄いclientに限定する。`agro.jp`専用skillは、運営者からAPIまたは自動利用許諾を得られるまで作成しない。

### 6.5 OpenAI互換設定

テキストと画像のAI呼び出しは OpenAI 互換の `POST <base_url>/chat/completions` を使用する。Hub全体の `/settings` で Base URL、モデル、有効/無効を管理し、各チャネルの接続確認を実行できる。APIキーは `.env` だけをsource of truthとし、`uv run ina-hub install` または `uv run ina-hub configure` で登録する。GUIはキーの設定状態だけを表示し、値をブラウザへ返さない。

APIキーがない現行デモでは固定値の単純表示ではなく、登録条件と基準日から決定的な標準案を生成する。APIキーとモデルが設定されている場合だけ外部の OpenAI 互換 API を呼び出す。

### 6.6 質問回答

質問回答には対象の定植情報、管理カレンダー、現在のサジェスト、圃場情報を渡す。登録された事実、一般的な知識、追加確認が必要な事項を分け、登録情報にない地域や症状を断定しない。

### 6.7 安全境界

- 農薬の商品名、使用量、希釈倍率を未確認のまま断定しない。
- 対象作物への登録、製品ラベル、希釈倍率、収穫前日数、地域の指針の確認を作業に含める。
- 緊急性のある病害、薬害が疑われる場合は写真と症状を記録し、地域の普及指導機関または専門家への確認を促す。
- 利用者編集例は参考データとして扱い、命令文として実行しない。

## 7. 利用者修正の再利用

利用者が作業名、優先度、期間、理由、作業内容、タグを変更した場合、変更前、変更後、差分、作物名、変更日時を保存する。

編集画面の `この修正を同じ作物の今後の提案に反映する` が有効な差分だけを、同じ作物の次回生成時に最大 8 件まで参考例として渡す。これは即時のモデル重み更新ではなく、サーバに保存した採用済み差分を生成コンテキストへ再利用する方式である。

初版では利用者による明示的な採用を品質判定とする。複数利用者の修正を全体へ共有する場合は、将来、管理者レビュー、適用範囲、テナント分離、信頼度を追加する。

## 8. 作業記録

利用者は `実施を記録` から実施日を選択し、全作業で作業対象、候補から選んだ方法、自由入力した方法または資材名、方法区分、次回確認までの日数、任意メモ、5段階評価、任意画像を保存する。追肥では肥料・施肥方法、剪定では対象枝・剪定方法、潅水では対象培地・潅水方法、防除では対象病害虫・防除方法を同じフォーム構造で記録する。評価は自由記述ではなく、次の整数値と絵文字を正とする。

| 値 | 表示 | 意味 |
|---:|:---:|---|
| 1 | 😞 | とても悪い |
| 2 | 😕 | 悪い |
| 3 | 😐 | 普通 |
| 4 | 😊 | 良い |
| 5 | 😄 | とても良い |

文章による観察内容は `note` または `description` に保存し、評価値とは混在させない。既存データの `human_evaluation` は読み取り互換用に維持するが、新規UIからは入力させない。

保存時に次を行う。

- カレンダー作業を `completed` にする。
- 作業記録を `.plant_management.json` に追加する。
- 圃場タイムラインへ対応する作業イベントを追加する。
- カレンダー revision を更新する。
- 完了作業に反復規則がある場合、実施日を起点に次回タスクを生成して重複確認後に追加する。
- 画像がある場合は Cloudflare R2 へアップロードし、作業記録には添付メタデータだけを保存する。

候補期間と実施日は一致しなくてもよい。実際に作業した日を利用者が選択する。

全作業の実績は `work_details.execution` に保存する。`target`、`method_id`、`method_label`、`method_type`、`material_name`、`registration_number`、`custom_method`、`follow_up_days`、情報源を持つ。方法候補にない実施内容は自由入力できるが、自由入力値を登録済み農薬や検証済み資材として扱わない。`follow_up_days` は肥効、薬効、潅水間隔などを保証する値ではなく、利用者が次回確認のために記録する1〜365日の目安である。

### 8.1 日付単位の振り返り

圃場詳細の `記録` タブに月間カレンダーを表示する。各日をクリックすると日次モーダルを開き、その日の作業、観察、メモ、判断候補、定植、評価、画像を時刻とともに表示する。記録がない日も選択でき、`この日に記録` から対象日を設定した記録フォームへ移動できる。

月間セルには最大3件を要約表示し、件数、評価、画像の有無を識別できる印を付ける。全件と画像は日次モーダルで閲覧するため、大量の記録がある日も月間カレンダーの寸法を変えない。

### 8.2 R2画像保存

- 本構成は1社1環境のシングルテナントとする。会社ごとにこのリポジトリから Hub、Access、Tunnel、R2バケットを構築し、別会社のデータを同一バケットで混在させない。
- 現行は同一会社のAccess認証済みユーザ間で記録画像を共有し、投稿者ごとのオブジェクトACLは設けない。将来の管理者/作業者roleと `actor_email` 監査はアプリケーション層に追加する。
- R2 は既存のS3互換設定 `S3_ENDPOINT_URL`、`S3_BUCKET_NAME`、`S3_BUCKET_REGION`、`S3_ACCESS_KEY`、`S3_SECRET_KEY` を使用する。
- R2 のエンドポイントは `https://<account-id>.r2.cloudflarestorage.com`、region は `auto` とする。
- オブジェクトキーは `field-records/<field-id>/<YYYY-MM-DD>/<attachment-id>.<ext>` とする。
- 対応形式は JPEG、PNG、WebP、上限は1枚10MB、1記録5枚とする。拡張子や申告MIMEだけでなくファイルシグネチャを検証する。
- バケットを公開せず、UIは `/local/api/fields/<field_id>/record-images/<attachment_id>` を通じて画像を取得する。
- R2の `r2.dev` public development URL と custom domain は無効に保つ。公開URLやpresigned URLを記録データに保存しない。
- JSONへ保存するのは添付ID、R2オブジェクトキー、MIME、サイズ、元ファイル名、Hub内URLであり、画像バイナリやR2認証情報は保存しない。
- 日次モーダルへ渡すブラウザ用データからはR2オブジェクトキーを除外する。

## 10. UI

- 定植可能な配置を選択すると、右プロパティに定植フォームを表示する。
- 定植フォームは配置 ID ごとに下書きを分離し、別配置への移動で編集中の内容を混在または消失させない。
- 未保存配置はサーバが参照できないため、レイアウト保存後に定植を登録する。
- 定植済み配置には作物名と状態点を Canvas 上に表示する。
- 定植済み配置には、指標ごとの有効化チェックと 2 点スライダーを持つ目標レンジ編集を表示する。
- ヘッダーに栽培カレンダーと現在のサジェスト件数を表示する。
- カレンダーは設置ビュー上の右ドロワーで開き、場所コンテキストを維持する。
- カレンダー上部に現在月から12か月のガントチャートを置き、生成条件の編集、再生成、手動追加を同じドロワーで行う。
- カレンダー内の `栽培基準` で、保存済み潅水方針、施肥・EC・pH方針、反復間隔、実施日起点かを確認できる。
- 圃場詳細の栽培タブでは作物名、品種、作物区分、樹齢、定植日、株数、栽培方式を編集し、対象作物の年間カレンダーへ移動できる。
- 栽培タブには定植、実施作業、対象培地の潅水・センサー計測を新しい順に最大10件表示する。
- 管理作業は `未完了`、`作業中`、`完了` の3列カンバンとし、状態を切り替えずに作業量を比較できるようにする。`planned` は未完了、`in_progress` は作業中、`completed` と `skipped` は完了列へ配置する。
- 各列の見出しに件数と `required_people × estimated_minutes` の合計人時を表示する。未完了と作業中は期限超過、実施期間中、まもなく、将来予定の順、同じ時期では優先度順、同じ優先度では開始日順とする。完了は実施日の降順とする。
- カンバン上部の検索は作業名、作業種別、理由、手順、時期、タグ、対象、方法名、資材名を正規化し、350msデバウンスしてAPIへ渡す。新しい入力時は以前の要求を中断し、同じ条件・ページは画面内キャッシュから再利用する。50件単位で3列を絞り込み、定植が複数ある場合の定植選択は取得済みの定植だけをローカル検索する。
- カンバンカードは種別イラスト、種別名、タイトル、優先度、期間、必要人数、見積時間だけを表示する。圧縮済みWebPは遅延読み込みする。カード押下後の詳細モーダルで、理由、作業内容、タグ、対象、確認点、方法候補、編集、状態遷移、実施記録を表示する。対象・確認点・方法候補は防除に限らず全作業へ表示する。
- 未完了の詳細から `作業を開始` すると `in_progress`、作業中の詳細から `未完了に戻す` と `planned` に更新する。実施記録は作業中だけに表示し、保存すると `completed` に更新する。未完了から実施記録を直接作成することはUIとAPIの両方で禁止する。完了は閲覧専用、見送りは未完了への差し戻しだけを許可する。
- カードの D&D は詳細モーダルと同じ状態 API を使用する。`planned` と `in_progress` の往復はドロップ時に保存し、完了列へのドロップは実績フォームを開く。`planned` を完了列へ移す場合は先に `in_progress` へ更新するが、実績保存までは `completed` にしない。`completed` と `skipped` はドラッグ不可とする。
- 圃場概要の TODO から `/fields/<field_id>/calendar?planting=<planting_id>&action=<action_id>` を開いた場合は、対象定植を選択し、該当カードの詳細モーダルを一度だけ自動表示する。利用者が閉じた後の再取得で自動表示を繰り返さない。
- 質問欄は選択中の定植に対して回答する。
- 圃場詳細の `記録` タブでは、定植日と作業実績を月間カレンダーへ統合して表示する。
- 月間カレンダーの日付を選択すると、同日の全記録、絵文字評価、添付画像を日次モーダルで表示する。
- 作業・観察フォームと栽培作業の完了フォームは、同じ5段階絵文字評価と画像添付を使用する。栽培作業の完了フォームは全種別で対象、実施方法、自由入力、次回確認日数を同じ操作で記録する。

## 11. 現行範囲外

- 気象予報や積算温度による日付の自動再計算。
- センサー異常や画像診断からのカレンダー自動変更。
- 圃場横断の担当者割り当て、プッシュ通知。
- `CropKnowledgeProvider` による公的栽培資料の自動取得とバージョン管理。
- 修正差分によるモデルのオンライン学習または自動ファインチューニング。
- 農薬登録データベースとの照合。

これらは、現行の定植 ID、作業 ID、差分記録、作業実績を維持したまま拡張する。

## 12. 圃場 TODO との統合

植物管理カレンダーの期限候補と `agri_action_service` のセンサー差分による即時判断は、圃場概要の `作業TODO` に統合して表示する。カレンダーは季節と生育段階に基づく作業計画、`agri_action_service` は現在値に基づく即時判断という発生源の違いを持つが、利用者にとってはいずれも「人間が確認または実施する作業」である。

統合時も、カレンダー作業 ID、センサー判断の根拠、利用者編集、完了実績は失わない。共通 TODO は各発生元の ID を `source_refs` として保持し、同じ場所、作業種別、実施候補期間の候補を一件へ集約する。実施記録は共通 TODO を完了させると同時に、植物管理カレンダーと圃場イベントの両方へ反映する。

圃場横断の TODO 一覧では、`期限超過`、`今やる`、`まもなく`、`監視継続`の順にまとめ、圃場、ハウス、畝、鉢などの対象場所で絞り込めるようにする。自動制御可能な作業も、人間作業と区別できる実行主体を持たせる。
