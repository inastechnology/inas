# Hub UI 状態別アクション設計原則

## 1. 目的

Hub の画面は、現在状態で実行できる操作だけを利用者へ提示する。単に全ボタンを並べてエラーにするのではなく、状態、入力条件、通信中かを先に評価し、次に行う操作が一意に理解できる UI とする。

本原則は、栽培作業、圃場記録、設置ビュー、機器、F/W、アプリ設定、個人設定のすべてへ適用する。

## 2. 表示規則

| 状況 | UI |
|---|---|
| 現在状態では意味を持たない操作 | ボタン自体を表示しない |
| 操作は正しいが入力や前工程が不足 | ボタンを無効化し、近くに不足理由と必要な前工程を表示 |
| 保存対象に変更がない | 保存を無効化し「変更されていません」と表示 |
| API処理中 | 二重実行を防ぎ、押したボタンを無効化して処理中表示 |
| 完了、廃止など変更不能な状態 | 閲覧専用表示に切り替える |
| 破壊的操作 | 正常な前段階を経た場合だけ表示し、主操作と視覚的に分ける |

無効理由は `aria-describedby` と `title` の両方へ関連付ける。色だけで状態や実行可否を表現しない。

### 2.1 情報から次の操作への近接性

- 利用者が値、警告、TODO、所属先を認識した直後に行う主操作が一つに定まる場合は、カード全体をその操作へのリンクまたはボタンにする。
- 遷移先は機能の入口ではなく、利用者が確認・編集したい対象を開いた状態にする。対象 ID、指標、タブなどを URL へ含め、一覧内で同じ対象を探し直させない。
- 例として、環境値カードは該当定植の該当指標の目標値編集へ、作業 TODO は該当作業の詳細モーダルを開いた年間カレンダーへ、機器の設置パスは該当配置へ遷移する。
- カード内に複数の同格操作がある場合はカード全体を一つの操作へ割り当てず、主操作と副操作を明示する。フォーム、D&D ハンドル、内部ボタンはカードの遷移と競合させない。
- フォーカス表示、操作名を含む `aria-label`、ホバー表示を用意し、色やマウス操作だけに依存しない。

### 2.2 動的集合の検索

- 会社、圃場、空間、培地、定植、デバイス、記録項目、作業など、運用中に件数が増える集合から選択または閲覧する UI は、同じ画面内にキーワード検索を置く。
- 名称だけでなく、ID、種別、所属場所、作物、同義語・表記揺れ用キーワードなど、その対象を利用者が想起する語を検索対象にする。
- 選択済み項目は検索によって消失・解除しない。全選択・全解除は現在の検索結果を対象とし、結果件数と空状態を表示する。
- ドロップダウンから候補を一つ選ぶ UI は、検索入力を開いたメニューの先頭へ内包する。検索欄と通常の `select` を上下に分離せず、利用者が候補を探す場所と選ぶ場所を一つにする。閉じている間は選択値だけを表示し、開いたときに検索、候補グループ、選択状態、空状態を同じポップオーバー内に表示する。
- 検索中も現在値、`選択なし`、`手動`、`カスタム入力`など操作上必要な固定候補は残す。選択後は元のフォーム値へ `input` と `change` を通知し、変更検知、必須検証、保存APIの契約を通常のドロップダウンと共通化する。
- 優先度、設置環境、状態など、数件に固定された列挙型の選択肢はドロップダウンを使い、検索を必須としない。
- 全件数が運用期間や会社規模とともに増え続ける集合、または初期取得が100件を超え得る集合は、検索条件をサーバへ渡してページングする。クライアント検索のために全件取得しない。
- 選択月、直近10件、現在の設置ビュー、作業種別、タグ、記録項目カタログ、実施方法候補など、画面の成立に全件が必要で取得範囲も閉じている集合は、取得済みデータをブラウザで絞り込む。入力ごとにAPIを呼ばない。

#### 2.2.1 現行コレクションの方式

| コレクション | 検索方式 | 理由 |
|---|---|---|
| 圃場一覧 | API検索、18件単位のページング | 会社規模に応じて増える入口データ |
| 全デバイス一覧 | API検索、24件単位のページング | 会社全体で増え、ID・名称・場所・種別・MOSFET用途名を検索する |
| 設置ビューのデバイス候補 | API検索、50件単位。選択済みIDは検索結果外でも保持 | 全国・全圃場のデバイスを候補として全取得しない |
| 圃場の栽培記録 | API検索、20件単位。種別・対象・期間をサーバへ渡す | 日々の手入力で増え続け、画像付き記録も含む |
| 栽培カレンダーの管理作業 | API検索、50件単位。状態・種別・期間をサーバへ渡す | 再生成と実績により長期的に増える |
| 月間記録カレンダー | 選択月をAPI/SSRで取得後、日付内はローカル | 表示月が明示的な取得境界になる |
| 配置パレット、配置済み対象、記録項目、タグ、作業方法、F/W候補 | ローカル検索 | 画面表示のため取得済みで、固定または小規模な候補 |
| 栽培タブの直近履歴、TODO | ローカル表示 | 10件または20件に制限した判断用サマリ |
| センサー・潅水グラフ、カメラ画像 | 期間・日付をAPIへ指定 | 全文検索ではなく時系列の取得範囲で制限する |

#### 2.2.2 API検索の共通契約

- クエリは `q`、業務フィルタは `status`、`kind`、`date_from` などの名前付きパラメータ、ページは `page` と `page_size` を使用する。
- 応答は `{items,total,page,page_size,page_count,has_previous,has_next}` とする。空結果でも `page=1` と件数を返す。
- 文字入力は350〜450msデバウンスし、新しい条件が入力されたら実行中の `fetch` を `AbortController` で中断する。同じ条件とページの結果は画面内キャッシュから再利用する。
- 検索中、取得失敗、0件、表示件数/総件数、次ページの有無を表示する。検索失敗時に現在の選択や未保存入力を失わない。
- 表記はNFKCと大文字小文字を正規化し、空白・区切り文字、`灌水`/`潅水`など既知の表記揺れを吸収する。
- 現行JSON repositoryは同じAPI契約の中でメモリ検索する。Turso repositoryへ移行するときは `WHERE`、全文検索インデックス、`LIMIT/OFFSET`へ押し下げ、APIとUIの契約を変更しない。

## 3. 栽培作業

| 状態 | 表示する操作 | 表示しない操作 |
|---|---|---|
| `planned` 未完了 | 編集、削除、作業開始 | 実績記録、完了 |
| `in_progress` 作業中 | 編集、未完了へ戻す、実績を記録して完了 | 削除、再度開始 |
| `completed` 完了 | 記録閲覧 | 編集、削除、状態変更、再完了 |
| `skipped` 見送り | 未完了へ戻す | 編集、削除、実績記録 |

実績記録 API は `in_progress` だけを受け付ける。カレンダー再生成では `in_progress`、`completed`、`skipped` を保持し、進行中または履歴の作業を置換しない。

カンバンの D&D もこの状態表を迂回しない。`planned` と `in_progress` の移動は対応する状態更新を行い、完了列へのドロップは実績入力を開くだけにする。実施日などの必須実績を保存するまで `completed` にしない。完了済みカードは移動不可とし、キーボードまたは詳細モーダルから同じ状態操作を実行できる代替手段を残す。

## 4. 機器ライフサイクル

| 状態 | 表示する操作 | 次状態 |
|---|---|---|
| `pending` 承認待ち | 承認、登録廃止 | `active` または `retired` |
| `active` 稼働中 | 停止 | `disabled` |
| `disabled` 停止中 | 再開、廃止 | `active` または `retired` |
| `retired` 廃止済み | 閲覧のみ | なし |

機器への設定送信は `active` のみ許可する。`pending` と `disabled` は設定の保存だけを許可し、`retired` は表示情報、動作設定、F/W対象を含む機器情報全体を閲覧専用にする。APIも同じ状態遷移と操作可否だけを受け付け、現在状態と競合する更新・送信は `409 Conflict` で拒否する。

## 5. フォーム

- 必須項目不足、変更なし、処理中、業務状態による禁止を別々の理由として扱う。
- 新規作成フォームは、必須項目が揃うまで主操作を無効化する。
- 編集フォームは、初期値から変更されるまで保存を無効化する。
- 記録フォームは、日時だけでは記録可能にしない。記録項目、メモ、評価、画像のいずれかを必要とする。
- AI、外部API、機器送信などコストまたは副作用のある操作は、入力条件を満たした場合だけ有効化する。

サーバーレンダリング画面では `/static/stateful-actions.js` を共通利用し、フォームごとの独自な変更判定を増やさない。React画面では `DisabledActionReason` と状態ごとの能力表を使う。

## 6. 試験

状態を持つ機能は、次を回帰試験へ含める。

1. 各状態で表示される操作と表示されない操作。
2. 禁止された遷移をAPIが拒否すること。
3. 前工程完了後に次の操作が有効になること。
4. 未変更、必須不足、処理中の二重実行を防ぐこと。
5. 完了・廃止状態が再読込後も閲覧専用であること。
6. 情報カードから遷移したとき、対象の編集行または詳細が直接開くこと。
7. 動的集合の検索、空状態、検索解除、選択保持が機能すること。
8. D&D と詳細モーダルの操作が同じ状態遷移規則に従うこと。
9. 検索可能な単一選択では、検索入力が開いたドロップダウン内にあり、選択後にフォーム変更が検知されること。
