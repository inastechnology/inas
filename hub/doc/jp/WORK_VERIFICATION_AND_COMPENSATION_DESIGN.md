# 圃場作業の確認と将来の報酬連携

更新日: 2026-07-22

## 目的

INAS Hub は、現場の作業者が実施内容を記録し、管理者が証跡を確認できることを優先する。確認済みの記録は栽培履歴として扱える。将来、報酬計算や送金を追加する場合も、作業状態とお金の状態を分離し、誤送金や後から変わる単価を避ける。

## 現在実装している流れ

    planned → in_progress → awaiting_review → completed
                           ↘ rejected → in_progress

- 管理者は作業へ担当者のメールアドレスを任意で割り当てる。
- 操作者は未割当または自分に割り当てられた作業を開始し、日付、評価、メモ、作業固有の値、写真を提出する。
- 提出時点では `awaiting_review` であり、公式の圃場イベントや AI の次回作業生成には使わない。
- 管理者は実施者と証跡を見て承認または差戻しする。差戻しには理由を必須とし、作業を `in_progress` へ戻す。
- 承認後だけ `completed` となり、公式履歴と次回計画へ接続する。
- 実施者、提出日時、確認者、確認日時、確認メモをサーバー側の認証情報とともに保存する。
- 差戻した提出を削除・上書きせず、再提出は別の作業記録として残す。
- 既存の完了記録は後方互換のため承認済みとして扱う。
- 管理者は圃場の作業画面で、認証済み実施者ごとの承認済み完遂数と確認待ち数を確認し、そのメンバーの担当・実施作業へ絞り込める。
- 操作者は本人の完遂数、確認待ち数、達成称号、次の節目までの進捗だけを確認できる。速さ、連続日数、メンバー間の順位は表示しない。

完遂集計は既存の作業ログを画面側で読み取り、`review_status=approved` だけを数える低コストな表示である。報酬額、支払可否、送金状態は持たない。現在の `admin` / `operator` は Hub 全体のロールであり、圃場単位の所属や権限ではない。担当者のメール入力も、正式なメンバー名簿の代替ではない。

## 次に追加するチーム管理

1. 圃場単位のメンバー、招待、在籍状態を管理する。
2. メンバーに圃場管理者、確認者、作業者などの権限を与える。
3. 作業割当は登録済みメンバーから選び、担当変更と引継ぎを監査する。
4. 期間指定、作業種別、差戻しを含む長期集計をサーバー側で提供する。
5. 通知は担当、期限、差戻し理由、確認結果を対象にする。

## 将来の報酬台帳

作業の `completed` をそのまま送金命令にしない。作業と報酬の間に、追記型の報酬台帳を置く。

作業割当時または開始前に、少なくとも次を変更不能な条件スナップショットとして保存する。

- 対象作業、圃場、作付け、作業者
- 計算方式: 固定額、出来高、時間単価など
- 単価、通貨、数量または承認可能な上限
- 合意日時と条件を提示・承認した主体
- 税・控除・雇用区分などを外部給与処理へ渡すための参照情報

管理者の作業承認で、条件スナップショットを参照した `compensation_earned` を一度だけ記帳する。画面上の完遂数や称号を記帳条件には使わない。訂正は元記録を消さず、取消・調整エントリで相殺する。実際の支払は `unpaid`、`queued`、`paid`、`failed`、`reversed` など、作業確認とは別の状態機械で管理する。

銀行振込、給与計算、決済サービスへの接続は別プロジェクトとする。本人確認、雇用契約、最低賃金、源泉徴収、手数料、再送、二重払い防止、取消、監査保存などは利用地域と支払方式に応じた確認が必要である。クライアント画面の操作だけで直接送金せず、サーバー側の冪等性キー、承認権限、台帳照合を必須にする。

## 今回の非対象

- 実際の賃金計算、給与明細、税務処理
- 銀行口座・ウォレット・決済事業者への送金
- 労働時間の打刻や位置情報による勤務証明
- 圃場単位の正式なメンバー権限
- メンバー間の順位、速度評価、連続勤務を促すストリーク

この段階では、将来の報酬台帳が信頼して参照できる作業証跡、管理者確認、承認済み実績の可視化までを提供する。
