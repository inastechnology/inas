# INAS エージェンティック農耕ビジョン

英語版: [../AGENTIC_AGRICULTURE_VISION.md](../AGENTIC_AGRICULTURE_VISION.md)

## この文書の位置づけ

この文書は、INAS が目指すエージェンティック農耕の思想と、長期的なプロダクト判断の基準を記録する。個別の API や画面仕様ではなく、新しいセンサー、作業機、AI 機能を追加するときに「何のために作るのか」「どこまで自動化してよいか」を判断するための文書である。

一文で表すと、INAS が目指すのは次の姿である。

> 農家の代わりに勝手に農業をする機械ではなく、圃場を観察し、根拠を説明し、人と機械へ安全に仕事を割り当て、結果から学び続けるオープンな農耕基盤をつくる。

## なぜエージェンティック農耕なのか

農業は、決められた時刻に設備を ON/OFF するだけでは成立しない。同じ作物でも、天候、土、培地、品種、生育段階、設備、過去の作業によって次に行うべきことは変わる。必要なのは単なる自動化ではなく、状況を読み、作業を組み立て、結果を確かめる循環である。

一方、すべての圃場へレールや専用ロボットを敷設する方法は、多くの既存農家にとって費用、地形、作物、保守の面で現実的ではない。INAS は圃場を機械へ合わせることを前提にせず、今ある圃場へ小さなセンサー、固定ポンプ、電磁弁、カメラ、人の作業、将来のロボットを組み合わせる。

この考え方では、エージェントは一台の万能ロボットではない。Hub が状況と目的を理解し、その時点で利用できる実行担当を編成する。

```text
圃場の事実
  センサー・画像・天気・作業履歴・人の観察
            ↓
Hub の農作業エージェント
  判断・説明・承認・割当・監視・記録・学習
            ↓
実行担当
  人 / 固定設備 / 外部サービス / 移動機械 / レール式装置
            ↓
結果の確認
  センサー反応・画像・使用量・収量・品質・人の評価
```

## 基本原則

### 1. 自動化より先に、良い判断をつくる

初心者が次の作業を知らない場合でも、INAS は適期、理由、方法、見送り条件、完了条件を示す。機械が作業できない段階でも、判断と記録を支援するだけで価値がある。自動化できる作業だけを製品の中心にしない。

### 2. 開ループの命令ではなく、結果を確かめる

「ポンプを30秒動かした」は設備の実行記録であり、「根域へ必要な水が届いた」とは限らない。作業には期待する結果を定義し、可能な限りセンサー、画像、使用量、収量、品質で確認する。確認できない場合は、成功と断定せず不確実性を残す。

### 3. 人は例外処理装置ではなく、主要な実行担当である

定植、剪定、収穫のような複雑で不可逆な作業では、人が最も適した実行担当であり続ける。INAS は人へ作業を丸投げせず、対象、理由、手順、危険、完了条件を分かりやすく提示し、記録の負担を減らす。機械化は人を排除するためではなく、人が判断すべき場面へ集中できるようにするために行う。

### 4. 任せる範囲は作業ごと、圃場ごとに広げる

一つの「全自動」スイッチで農業全体を自動化しない。潅水は自動、施肥は提案と承認、剪定は画像候補、収穫は人が実施、という混在を正しい状態として扱う。同じ作業でも、小さな鉢と露地の大区画では自動化レベルが異なってよい。

### 5. 能力と到達範囲を分ける

機器定義は「何ができるか」を表し、設置情報は「どこへ作用できるか」を表す。潅水能力を持つ機器が圃場内に存在しても、対象の畝へ配管されていなければ、その畝の実行担当にはできない。ロボット、外部サービス、人の役割も同じ考え方で扱う。

### 6. 既存圃場と小さな導入を尊重する

最小構成は、スマートフォンと作業記録だけでもよい。次にセンサーを一つ、ポンプを一つ、カメラを一つ追加できる。既存の点滴配管、市販ポンプ、SwitchBot のような外部機器も、安全条件を満たすアダプタとして利用できる。高価な専用設備を導入できる人だけの仕組みにしない。

### 7. 初心者には簡単に、上級者には深く

通常画面では、電子回路、端子、通信方式、内部 ID より先に「何を測るか」「何を動かすか」「どの作物へ作用するか」を示す。小学生でも目的が理解できる入口を用意し、校正値、しきい値、通信、プロンプトなどは上級者設定で調整できる二段構成にする。

### 8. 根拠と不確実性を同時に示す

AI の提案には、作物情報、観測値、公開資料、利用者の記録など、判断に使った根拠を残す。一般値は開始点であり、製品ラベル、地域基準、土壌分析、圃場実績を優先する。確信度が低い場合やデータが古い場合は、それを隠さず、追加観測または人の判断を求める。

### 9. 安全は AI の賢さではなく、構造で守る

安全上限、最小間隔、タイムアウト、物理停止、重複防止、受付応答、完了確認、監査履歴を、モデルの出力とは独立して実装する。通信断、センサー欠測、異常流量、対象不明では安全側に止まる。不可逆性が高い作業ほど承認と事後確認を強くする。

### 10. オープンで修理でき、データを利用者へ返す

H/W を購入すれば誰でも製作でき、必要なら完成品も購入できる形を目指す。デバイス定義、通信、判断履歴を開き、特定ベンダーだけが修理・拡張できる構造を避ける。圃場データと作業履歴は利用者の資産であり、ローカル Hub を中心に、エクスポート、移行、外部連携ができるようにする。

## 共通の農作業ループ

すべての作業は、次の循環へ近づける。

1. 観測する: 現在の状態と履歴を集める。
2. 評価する: 目標、適期、開始条件、見送り条件、安全条件と比較する。
3. 提案する: 作業、理由、期待効果、リスク、実施期間を示す。
4. 承認する: 自動化レベルに応じて人または方針が承認する。
5. 割り当てる: 能力と到達範囲を満たす人・機器を選ぶ。
6. 実行する: 上限付きで実施し、受付、開始、中止、完了、失敗を追跡する。
7. 確認する: 期待した変化が起きたかを確かめる。
8. 学習する: 結果を次回の時期、量、方法、担当選択へ反映する。

AI の文章生成だけでこのループが完成したとはみなさない。作業状態、承認、機器能力、接続先、実行結果、検証値が構造化されて初めて、エージェンティックな実行基盤になる。

## 自動化成熟度

| 段階 | Hub の役割 | 利用者・機器の役割 |
|---|---|---|
| L0 記録 | 作業と観測を保存する | 人が判断して実施する |
| L1 ガイド | 適期、手順、見送り、完了条件を示す | 人が判断して実施する |
| L2 提案 | 圃場データから作業候補と根拠を示す | 人が採用・変更・却下する |
| L3 承認付き実行 | 対象へ接続された機器へ上限付きで依頼し、結果を記録する | 人が承認し、異常時に対応する |
| L4 条件付き自律 | 限定された作業と環境で自動判断・実行・確認する | 人が方針と例外を管理する |
| L5 協調農耕 | 複数の人・機器・作業を季節全体で調整する | 人が目的、品質、経営、倫理を決める |

成熟度は製品全体へ一つ付けるのではなく、作業、圃場、設備単位で管理する。L4 の潅水と L1 の剪定が同時に存在してよい。

## 作業ごとの目指す方向

- 定植・植え替え: 苗、場所、株間、深さ、天候、初回潅水をガイドし、将来は位置決め、掘削、把持、活着確認を能力別に機械化する。
- 潅水: 土壌水分、天気、直近履歴、流量、タンク、対象配管を確認し、最初に閉ループ自動化する。
- 施肥・液肥: 肥料カタログ、残存肥効、降雨・潅水、土壌分析、生育と品質を合わせ、過剰施肥を避ける。FGT などの実行機器は調製、投入、攪拌、洗浄、潅水を検証可能な工程として扱う。
- 防除: 症状と原因を断定せず、観察、同定、登録・ラベル確認、物理的対応を優先し、薬剤は強い承認境界を持つ。
- 剪定: 画像上の候補提示から始め、品種、花芽、結果枝、樹勢、切断位置の認識精度を検証してから機械化する。
- 収穫: 成熟度、天候、用途、品質を提案し、収量・糖度・傷みを次の栽培判断へ返す。把持と搬送は別能力として扱う。

## やらないこと

- LLM が出した文章を、そのまま機器へ送って作動させない。
- データがない状態で、一般論を圃場固有の事実として断定しない。
- 「完全自動」という宣伝のために、失敗時の人の負担や物理的危険を隠さない。
- 新しい作物ごとに専用デバイスを増やし、再利用できない構造にしない。
- 専門用語や内部設定を一般利用者へ露出して、利用者の知識不足をエラー扱いしない。
- ロボットやレールを否定しない。ただし、それだけを唯一の正解または前提にしない。

## 成功を測る指標

エージェンティック農耕の成功は、無人時間や実行回数だけで測らない。

- 初心者が必要な作業に気づき、理由を理解できたか。
- 作業漏れ、重複作業、過剰潅水、過剰施肥を減らせたか。
- 異常時に安全に止まり、原因究明に必要な履歴が残ったか。
- 作業時間、資材、水、電力を減らしながら、収量と品質を維持・改善できたか。
- 利用者が提案を修正・拒否でき、その結果が次回へ反映されたか。
- 小規模な導入から、データや設備を捨てずに段階的に拡張できたか。
- 作物、土壌、水系、生態系への負荷を減らせたか。

## 実装判断のチェックリスト

新しい機能や機器を追加するときは、少なくとも次を確認する。

- 利用者が達成したい農作業上の目的は何か。
- どの観測事実に基づき、どの不確実性が残るか。
- 作業の開始、見送り、中止、完了条件は何か。
- 必要な能力と、対象へ届くことをどこで宣言するか。
- 失敗したとき、安全側へ止める境界は AI から独立しているか。
- 実行結果を何で確認し、次の提案へどう返すか。
- 初心者向け画面から内部実装の都合を取り除けているか。
- 既存 DB、既存機器、手作業だけの利用者を置き去りにしないか。
- 利用者が提案、承認、データを自分で管理できるか。
